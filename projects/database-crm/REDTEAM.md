# Red-team review of BRIEF.md (2026-11-04)

Method: 6 independent adversarial reviewers (sync integrity, access/security, metrics truth, ops/cost/legal, completeness vs your words, skeptical lead) produced 105 unique findings; the top 40 (all critical/high/medium up to a cap of 40) were each attacked by a separate skeptic agent; 40 survived (0 refuted outright; some were marked partly/overstated and corrected). 65 lower-severity findings were not verified (not dropped silently; they are in the workflow journal). A Fable-level decision agent folded the survivors into the changes below. Nothing here is applied to BRIEF.md yet unless marked.

## Go / no-go
GO for the UI preview now, with the UI-SPEC changes above applied before screens are built (they are mostly labels, one table, two actions and a mock-data fix; nothing structural). GO for the overall plan and architecture (Option B, Supabase Pro, Outreach shell, read-only sheets) once the BRIEF edits above are pasted in and the 5 questions are answered; 'approve all defaults' is a valid answer. NO-GO for WS2 (schema) and WS3 (scanner) until the 5 answers and the 2 pilot sheet shares plus the new service account exist; WS4 waits for P1 (scanner numbers table vs each sheet's Stats tab). The three biggest risks: (1) 'Reached' has no reliable writer today, so the headline KPI depends on Question 1 and on people actually pressing 'Mark contacted' or editing Status; (2) removals and Do-not-contact cannot touch the bots' sheets or the Outreach sender, so the fail-safe is durable only inside Database until the Blacklist export ships with Outreach; (3) scanner correctness (grid-limit 400s, per-tab isolation, re-import of purged keys, tab renames) is only provable in the pilot with real sheets, and the Drive modifiedTime gate is unverified, so the 2-minute promise is 'measured, not promised' until P1 passes.

### 5. s6 Removal flow + s7 #12 + s4 tables

**Why:** The brief has no memory of a removal. A full resync (flag 9), a re-added sheet, backfill or a sibling row from another sheet re-inserts a purged lead as new. The user's core fail-safe would look like it works and not.

### 9. s6 last paragraph ('No role has a database DELETE right') + s7 #12

### 11. s4 scanner + s7 #4, #5, #9, #16 (scanner rules)
**Change:** Add a 'Scanner rules' list: (1) Per-tab state (cursor last_seen_row, anchor hash, last_ok_at, last_error, header hash) keyed by Google sheetId (gid), never by title; tab is an attribute of the source row; niche comes from the Niche column, not the tab title. (2) Lead tabs = row 1 has Place Id AND Company Name AFTER dropping tabs whose lower-cased name is in the bot's RESERVED set (leadbot.py:43-44: all leads, dashboard, seen, searches, snapshots, run log, meta, rules, stats, ...) or starts with 'OLD '; the wizard shows dropped tabs with the reason. (3) Every tail range starts AT the anchor row (A{last_seen_row}:CZ), so it is always inside the grid; the first returned row is compared to the anchor hash and the rest are new. (4) Tab titles are quoted with '' escaping; batchGet is chunked at 40 ranges. (5) Any 400 on a batch re-runs that sheet's tabs one by one (bisect); a tab that still fails gets last_error and a resync queue entry while the other tabs keep syncing; per-sheet last_synced is set only when every tab read succeeded, else 'N tabs failing'. (6) The ~10 min sweep reads the whole Place Id + Status columns per tab, diffs against stored (gid, row, place_id), and fetches any row whose Place Id is new or changed (one batchGet of those row ranges); the cursor stays at the last non-empty row; rows with no usable key are parked as 'incomplete'. (7) Missing in source is judged per spreadsheet across all its lead tabs, only after a Place Id is absent from 2 consecutive complete sweeps, never after a sweep that errored, was truncated or hit 429; if more than min(50, 5% of active rows) vanish in one sweep, create ONE sheet-level Approvals item (Keep all / Confirm all) and mark the sheet 'needs attention'; a tab whose non-blank Place Id count drops >20% or stops being detected as a lead tab is flagged 'key column changed' and skipped for missing-detection. (8) lead_sources with unique (sheet_id, place_id) is the ONLY table the scanner writes; survivorship into the lead entity: Do not contact in any source wins, then Not interested, then the furthest progress step; unknown free text ignored; first_seen = min; display fields from the source with the most non-empty contact fields, ties to oldest; the drawer shows disagreements. (9) Read budget: log every Google call (including spreadsheets.get and retries) in scan_runs; budget per tick = 45 minus reads in the trailing 60 s, spent in the order live tails, safety net, sweep; stagger the safety net at tick % 5 == sheet_index % 5 and the sweep at tick % 10 == sheet_index; on 429 write blocked_until = now()+65 s into scanner_state and end the invocation (no sleeping). (10) valueRenderOption UNFORMATTED_VALUE, dateTimeRenderOption FORMATTED_STRING. (11) Drive modifiedTime gate is a feature flag OFF by default; the tail read runs every 60 s tick (about 11 reads/min idle); the flag is turned on only if the pilot shows the gate trips within 30 s. (12) The scanner never ingests the app-owned export sheet.

**Why:** Confirmed failure modes the brief does not handle: a tab that fills exactly to its grid (28-30% chance per 200-row cycle) returns 400 'exceeds grid limits' and kills the whole batchGet for that sheet; tab renames would storm the Missing queue; the v4 All Leads tab would double rows; a hand-added row above the cursor is never fetched; a stateless token bucket cannot hold a budget; the recon told the builders not to rely on modifiedTime for a 1-minute SLA.

### 15. s6/s7 #4 'Run health and alerting' (new)
